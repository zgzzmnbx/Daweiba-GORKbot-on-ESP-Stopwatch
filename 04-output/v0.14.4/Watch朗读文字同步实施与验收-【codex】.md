# Watch 朗读文字同步实施与验收

- 日期：2026-09-26
- 电脑端源码：v0.14.4-dev
- Watch 固件及设备 app0：v0.9.1-dev，未在本轮写入

## 问题与改动

原流程在 TTS 完成时就通过普通机器人状态刷新把文字发到 Watch，随后才开始 BLE 音频传输。传输等待期间，气泡已显示，因而文字与声音明显错开。

现在对话页的「Watch 朗读」按以下顺序执行：

1. 合成当前轮语音，不自动显示 Watch 文字。
2. 通过现有加密 BLE 音频通道发送全部 PCM/Opus 数据，等待设备确认 `COMMIT`。
3. 在同一设备写入锁内发送对应文字气泡。
4. 下达 `PLAY`，等待设备报告 `PLAYED`。

AI 回答作为朗读来源时，同样抑制问答及 TTS 阶段的提前显示。单独「小人显示」仍即时显示。页面通过后端能力标志 `watch_speech_sync` 判断新时序是否可用；旧后端会提示重开 Gork。失败、停止和过期代际不会提前显示待播文字；若文字已发出而播放失败，客户端尝试清除气泡。

## 验证

- Python 全量相关回归：99 passed，2 个现有依赖弃用警告。
- 页面 Node 回归：49 passed。
- Electron 回归：21 passed。
- 最后补充的「发送 idle 表情后提交文字」定向回归：43 passed，2 个相同依赖警告。
- 定向测试确认操作顺序为 `COMMIT → idle 表情 → 文字 → PLAY`，并覆盖原文、AI 回答、取消、代际失效和旧后端拦截。

## 运行与真机门禁

首次核对时 `http://127.0.0.1:8766/api/health` 无法连接。用户正常启动 Gork 后，正式后端 `/api/health` 实测报 `0.14.4-dev` 与 `watch_speech_sync=true`。用户随后在当前 Watch 上测试对话页朗读，反馈文字与声音“同步，很好”。这完成本轮同步时序的真机听看验收；未另外逐字确认该句的完整性，也不据此扩大到停止、掉线或长稳验收。设备报告 `PLAYED` 仍须与实际听感分开记录。
