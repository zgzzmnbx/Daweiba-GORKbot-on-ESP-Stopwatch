# v0.7.0 纯 BLE 设备录放音方案

更新：2026-09-21。状态：已获开发批准；v0.7.0-P0 音频探针源码、电脑工具、模拟测试和构建完成，未烧录，P1–P4 未通过。电脑工作台仍 v0.6.0，设备仍 v0.5.0。已实现协议及测试版边界见 `12-v0.7.0-P0音频探针协议与操作-【codex】.md`，下文仍是完整 v0.7.0 目标，不能把目标功能当成本次完成项。

## 1. 用户决定与范围

用户要求 StopWatch 自身收音与出音，并选择“目前先考虑纯蓝牙”。本阶段设备与本电脑之间仅使用 BLE，不引入 Wi-Fi、不开放局域网端口、不切换成小智固件，不替换现有 Grok bot 视觉。

拟定闭环：设备按键开始录音 → BLE 上传音频 → 本机工作台经现有独立语音服务转写 → 工作台展示/编辑文字并请求回读 → BLE 下载音频 → StopWatch 扬声器播放。按住/松开作为首选交互，具体按键要先核对现有短按、长按和 A+B 设置入口，不能直接覆盖原行为。

首版半双工，收音与播放不同时进行；播放中再次按说话键先停止播放再录音。首轮仍是转写与回读，不默认增加 LLM 问答、唤醒词、持续监听、声学回声消除或脱离电脑的独立助手。设备真实开始/结束播放驱动 speaking/idle，不能以电脑传输完成冒充声音播完。

“纯蓝牙”限定设备到电脑；电脑语音服务仍默认全本地。选择云端 ASR/TTS 仍需各自独立上传许可，不能因为新增设备麦克风而默认开上传。

## 2. 已核对事实与未验证项

- 官方硬件具备 MEMS 麦克风、ES8311、AW8737A 功放与扬声器；音频电源和功放由 M5IOE1 控制，必须沿用官方初始化方式，不能当作普通直接 GPIO。
- ESP32-S3 支持 BLE，不支持经典蓝牙；本方案是自定义 GATT 数据传输，不是 Windows 标准蓝牙耳机，也不承诺 LE Audio。
- 本地 `ble_control.h` 的 `kMaxCommandLength=20` 是当前应用协议上限；现有写命令/读通知特征只处理表情与文字，未实现设备音频。不能把“BLE 所有传输都只能 20 字节”当成硬件限制。
- Bleak 提供协商后的 MTU 和 `max_write_without_response_size`，但具体 Windows 控制器、固件栈和同时渲染时的持续吞吐必须实测，不能用无线 PHY 标称速率代替。
- 尚未验证：麦克风/扬声器驱动在本工程锁定库上的可用性、录放切换、音质、PSRAM 余量、BLE 音频吞吐与显示并行性能。

## 3. 数据量与首轮策略

以下是 PCM 数据量计算，不是实测性能，均不含传输头和重传：

| 数据 | 净音频字节率 | 10 秒数据量 |
| --- | --- | --- |
| 上行：16 kHz / 16 bit / 单声道 | 32,000 B/s | 320,000 B |
| 下行：24 kHz / 16 bit / 单声道 | 48,000 B/s | 480,000 B |

先验证短句整段传输：录音缓存在 PSRAM，录完再传；TTS 收到完整 WAV 后验证格式和大小，再把有效 PCM 交给设备。设备收齐并确认完整后播放，优先保证不会漏字、拼接旧音频或播放坏数据。建议原型录音先限 10 秒，最终上限根据可用内存和实测速率确定；不得静默截掉超长录音/回读。

实时边录边传不是第一阶段承诺。若实测净吞吐不足，需要评估分块 ADPCM 等压缩，电脑端解码回语音服务要求的 PCM；编解码、音质和 CPU 开销都必须测试。不能未经说明改为低采样率并仍声称满足 16 kHz 输入规格，也不能自动转用 Wi-Fi。

验收时报告上下行净 B/s、10 秒音频传输耗时、松键到转写/首声延迟、重传次数、帧率和空闲内存；体验可接受阈值根据原型结果与用户确认，不预先宣称“低延迟实时”。

## 4. BLE 协议设计约束（待原型冻结字节布局）

1. 保留旧 UUID 与 20 字节表情/气泡协议的语义，新增版本化音频能力/控制、上行通知和下行写入特征；不能直接扩大旧结构而破坏控制台。
2. 握手声明协议版本、支持格式、最大录音/回读字节数、接收窗口和分包容量。包长度按实际协商限制扣除协议头计算，兼容小 MTU；低吞吐时明确提示，不假报音频已就绪。
3. 音频事务使用连接代号、transfer_id、方向、格式、总长度与序号/偏移；定义 BEGIN、DATA、END、ACK/NACK、CANCEL、PLAY、STOP、PLAY_STARTED/PLAY_ENDED/ERROR。对错序、重复、缺包、越界和断线中止有确定处理，不将旧事务拼入新录音。
4. 大块数据可采用通知/无响应写入配合应用层窗口确认和流量控制；不能沿用每 20 字节等待一个文本回执的音频发送策略。无响应写入提交成功不等于设备已经收齐或播放。
5. 一个 BLE 调度器协调控制/表情/气泡/音频；STOP/CANCEL 优先、每批音频有上限，不能让整段数据持有写锁直到发送完才允许停止。设备本地按键停止不等待电脑 ACK。
6. 继续加密绑定、只允许当前授权控制端；音频通知发送前也必须检查授权，不能只保护写入或只检查特征可读权限。不得退化为开放麦克风广播。
7. 断开/换轮/重连清理音频事务和队列，不自动重录、不重放旧音频。窗口、超时和最大重试次数有界，校验失败不播放。
8. 设备录音必须有用户明确按键动作与屏幕提示；工作台未连接/未启用设备语音时不启动远程录音，首版不增加常驻后台监听。原始录音默认只在内存，日志不保存音频内容或私有文字。

## 5. 工程边界

- 固件：增加音频电源/Codec/I2S 管理、PSRAM 缓冲、录放状态机和音频 GATT 通道；保留显示驱动、局部刷新、设置、亮度、电量、顶部调试字及既有动画。
- 电脑端：扩展现有工作台的“设备音频”入口与 BLE 调度；仍通过 HTTP 调用独立语音服务，不导入对方源码、模型、venv 或 Key。
- 语音服务：继续接收完整 PCM16/mono/16k WAV，返回完整 WAV；优先不改服务接口。有缺口先形成具体契约变更，不另起不兼容实现。
- 浏览器不再负责设备模式的录音或播音，但保留已有“电脑麦克风/扬声器”模式作为回退。两种模式不能同时占用一轮会话；服务 session/turn 与设备 transfer/generation 显式映射。
- 音量、停止、超长错误、设备离线及授权状态在工作台可见；设备失联不能自动改用电脑麦克风偷录。

## 6. 实施与验收顺序

| 阶段 | 工作 | 通过条件 |
| --- | --- | --- |
| P0 软件可行性 | 查锁定的 M5Unified 音频支持和官方例程；冻结协议头、资源预算与按键冲突处理；编解码/分包纯软件测试 | 可编译探针、边界测试、无原固件行为回归；此阶段不烧录 |
| G1 真机写入授权 | 重新识别端口/MAC，复核既有本地恢复点和实际写入范围 | 获得当次烧录指令；不改 eFuse/分区或整片擦除 |
| P1 本地录放 | 设备先低音量播放测试音，再按键录音、本机回放 | 用户听验、录音电平、录放切换与按键停止正常 |
| P2 BLE 通道 | 在电脑与设备双向传确定性测试数据，记录净吞吐、限流、错包/断开/取消 | 数据完整、上限明确、20 次取消不复活旧事务，陌生端不得获取麦克风数据 |
| P3 语音闭环 | 设备录音→本地 ASR→编辑/回读→设备播音 | 真人话语可辨、数字无异常丢失，状态来自设备实际播放事件 |
| P4 回归与交付 | 原表情/气泡、设置、USB 控制、蓝牙重连、音量、帧率、30 分钟运行 | 分别记录构建、写入、传输实测和人耳/实屏验收，不互相替代 |

备份沿用 `04-output/backups/2026-09-20-before-voice-companion-v0.5.0/`；不重复计算文件 SHA-256，不公开完整 Flash。协议完整性检查与固件文件哈希是不同事项，仍应确保丢包/坏包不播放。
